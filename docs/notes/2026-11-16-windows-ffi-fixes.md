# 🪟 Windows FFI 実装の 4 件の不具合

<!-- 句点は他の文書と同じく「。」で統一している． -->
<!-- textlint-disable ja-technical-writing/ja-no-mixed-period -->

## 📝 要約

serdevmock と com0com で結合テストを流し、Windows の FFI 実装に不具合を 4 件見つけて直した。
うち 2 件は連鎖しており、1 件目の例外が 2 件目のハンドル漏れを表に出した。
本ノートは、Windows API の値の取り違えと、PHPUnit の中でだけ起きた FFI の挙動を残す。

## 🧭 背景

結合テストの基盤（#23）を手元の Windows で試した。
com0com の COM10 ⇔ COM11 を使い、COM11 で serdevmock を動かして COM10 を開いた。
その過程で、次の 4 件が見つかった。

表 1. 見つかった不具合と症状

| 不具合 | 症状 |
|---|---|
| 書き込みに上限が無い | 相手が読まないと `write()` が戻らない |
| FFI の型が壊れる | 同じプロセスで 2 回目に開くと `FFI\Exception` が出る |
| ハンドルが漏れる | 設定に失敗すると、同じポートを開けなくなる |
| ストップビットの写し間違い | 2 ビットを指定すると 1.5 ビットになる |

## ✅ 判断

- 書き込みの上限は「1 文字の最大送信時間 × バイト数 + 1 秒」とした。
  1 文字は最大 12 ビット（スタート・データ 8・パリティ・ストップ 2）と見積もる。
- 上限に達した `write()` は例外にせず、書けたバイト数（0 を含む）を返す。
  Linux と macOS も非ブロッキングの `fwrite` で同じ振る舞いのため、揃えた。
- `SetCommTimeouts` の失敗は例外にする。見逃すと、上限の無い設定のまま使われる。
- FFI インスタンスはプロセス内で 1 つだけ作り、静的プロパティで保持し続ける。
- 開いた後の設定で例外が出たら、ハンドルを閉じてから投げ直す。
- ストップビットは `match` で DCB の値へ写し、未対応の値は例外にする。
- 値の変換は静的メソッドに切り出し、`@internal` のまま公開した。
  FFI の無い OS でも、変換規則を単体テストで確かめられる。

試験の組み立ては次のとおりとした。

- 相手が読まない書き込みは、子プロセス（`proc_open`）で試す。
  修正前の実装は戻らないため、同じプロセスで試すと PHPUnit ごと止まる。
  親は 15 秒の期限で子を待ち、期限切れを失敗として扱う。
- 設定の失敗は、`applyConfiguration()` が例外を投げる無名サブクラスで再現する。
  その後、同じポートを通常どおり開けることを確かめる。

## 🔀 代替案と棄却理由

- 上限に達した `write()` を例外にする案は採らなかった。
  PySerial は書き込みのタイムアウトを専用の例外で知らせる。
  ただ、本ライブラリの API の約束が変わるため、別途判断する論点として残した。
  追記: v2.0.0 で方針を改め、全 OS で `TimeoutException` を投げるようにした。
  送れたバイト数は `getBytesWritten()` で取り出せる。
- 書き込みの上限を固定値だけにする案は採らなかった。
  低いボーレートで大きなデータを送ると、正常な送信まで途中で打ち切られる。
- FFI の型破損の原因を突き止めてから直す案は、時間を区切って諦めた。
  PHPUnit の外では再現せず、再現条件を絞り込めなかった。
  共有は回避策であり、その旨をクラスのコメントに残した。

## ⚠ 想定外だった挙動

### COMMTIMEOUTS の 0 は「待たない」ではない

修正前は `WriteTotalTimeoutMultiplier` と `WriteTotalTimeoutConstant` を 0 にしていた。
読み込み側の感覚で「すぐ戻る」と読みがちだが、書き込みでは「上限なし」を意味する。
相手が読まないと送信バッファが空かず、`WriteFile` は戻らなかった。
修正後は、9600 bps で 64 バイトを書くと約 1.1 秒で戻った。

### DCB.StopBits は 1 を引いても合わない

DCB の `StopBits` は 0 が 1 ビット、1 が 1.5 ビット、2 が 2 ビットである（`winbase.h`）。
修正前は「ビット数 − 1」で写していたため、2 ビットの指定が 1.5 ビットになった。
1 ビットは偶然正しく写るため、既定の設定では気づけない。

### PHPUnit の中でだけ FFI の型が壊れる

試験 3 件を 1 件ずつ流すと通り、まとめて流すと 2 件目以降が失敗した。
2 件目は、DCB のフィールドへの代入で次の例外が出た。

```text
FFI\Exception: Incompatible types when assigning to type 'char'
```

インスタンスごとに `FFI::cdef()` を呼んでいたことが関係する。
同じ手順を PHPUnit の外のスクリプトで繰り返しても、再現しなかった。
FFI インスタンスを共有すると、まとめて流しても通るようになった。

### 例外がハンドル漏れを表に出した

3 件目は、ポートを開く段階で失敗した。
2 件目の例外で設定が中断し、排他で開いたハンドルが閉じられずに残っていた。
COM ポートは排他で開くため、同じプロセスでも二度と開けない。
FFI の不具合だけを直していたら、この漏れは隠れたままだった。
